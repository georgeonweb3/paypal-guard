Guarded Agent Checkout

An AI agent that can pay is an AI agent that can be robbed. This is the guard that stands in front of the money.

▶ Watch the demo video GitHub repo Devpost entry

01How it works

An AI agent proposes a purchase. Before any money moves, the guard runs two layers of checks and returns a verdict.

Layer 1Pre-flight checks

  • Merchant sanity — is the merchant known, or is it on a block list?
  • Price sanity — is the quoted price within 1% of the reference median, or is the agent being overcharged?
  • Quote consistency — does the total equal unit price × quantity + shipping?

Layer 2Spend policy

  • Per-transaction cap — no single payment above the owner's limit.
  • Daily limit — total spend per day stays inside a set budget.
  • Owner freeze switch — the owner can freeze all payments instantly.

AI · inside the appAgent proposer

  • A live LLM call (src/ai.mjs) turns a plain-English goal — "buy a USB-C docking hub from AnkerDirect, keep it under $50" — into the purchase proposal the guard checks.
  • Runs on a local Ollama model by default (recorded runs: qwen3:4b, $0, no API key), or any OpenAI-compatible endpoint.

AI · inside the appRisk reviewer

  • A second LLM call reads the proposal plus the guard's results and flags what rules cannot see: lookalike merchants, urgency and pressure wording, goals that contradict the proposal.
  • It can HOLD a payment the rules allowed. It can never clear a BLOCK, edit an amount, or raise a cap.
  • Proof: a goal worded "URGENT, no time to explain, just pay whatever it costs" passed every rule check — and the AI reviewer held the payment for a human. Full run: evidence/agent-run-pressure.txt in the repo.

The verdicts

ALLOW

The checks pass and the PayPal sandbox payment executes.

HOLD

Something needs a human. Nothing moves until a person approves.

BLOCK

Rejected outright. No PayPal call is ever made.

The checks are ported from the author's earlier agent-safety work: tgp-guard (pre-flight checks for autonomous agents) and Aegis (on-chain spend control for agents on Base). Same semantics, new rail: PayPal.

Sandbox lesson 1Merchant country decides

The merchant account's country decides whether it can receive payments. A merchant in a send-only country gets seller-restricted on every checkout. The completed run used a US sandbox merchant.

Sandbox lesson 2Use the Pay Now flow

The default review checkout flow can hang. The Pay Now flow (user_action: PAY_NOW, NO_SHIPPING) completes. Funding source matters too: a card-funded approval captured COMPLETED, while a bank-funded one captured PENDING.

04Run it yourself

Clone the repo and run the demo locally.

terminal
node demo.mjs all --fresh
  # all six scenarios
node demo.mjs allow
  # one scenario: allow | merchant | overlimit | offmarket | hold | freeze
node demo.mjs capture <ORDER_ID>
  # capture an approved sandbox order

Zero dependencies. Node ≥ 20.

Without PayPal sandbox credentials the demo runs in a clearly labelled MOCK mode — simulated lines say SIMULATED. Mock output is never a PayPal result.

With sandbox credentials (PAYPAL_CLIENT_ID / PAYPAL_CLIENT_SECRET from a sandbox app at developer.paypal.com) the ALLOW path makes real sandbox calls.
